# Knowledge Base (kb/)

Internal knowledge base of **Minecraft behavior** (sourced from https://minecraft.wiki)
mapped onto **this codebase's implementation**. It exists so that when someone asks to
modify a block, entity, or mechanic, the change is made with the vanilla specs, our
implementation details, deviations, and machine gates all in view.

## How to read (protocol for every session)

1. **Look up before touching.** When a request mentions a block/entity/mechanic, first
   check `kb/index.json` (grep the `name`/`tags`), then read the entry file it points to.
2. **Honor the entry's sections:**
   - *Vanilla specs* — what the wiki says the thing does (hardness, slots, behavior).
   - *Our implementation* — exact code anchors (file:line-style) that realize it here.
   - *Deviations / limitations* — where we intentionally differ; do not silently "fix"
     these unless the request asks for parity.
   - *Ruleset when modifying* — gates to run and invariants to keep (slot counts,
     tile pins, worker parity, golden-frame MAE, etc.).
3. **No entry?** Fetch the wiki page (`https://minecraft.wiki/w/<Title>`), create the
   entry from `_templates/entry.md`, fill in code anchors by grepping `src/`, then do
   the work.
4. **After implementing**, update the entry (anchors that moved, deviations changed)
   and bump `updated_at`. Entries are allowed to drift stale but never silently wrong.

## Quality bar (chest-standard)

`kb/blocks/chest.md` is the reference entry. A finished entry has: vanilla
numbers in tables (not adjectives), a per-concern anchor table under `Our
implementation`, an honest `Deviations / limitations` list, machine gates +
invariants under `Ruleset when modifying`, and linked `Open work`. New stubs
from `scripts/kbExpand.mjs` are intentionally below this bar (`status: absent`);
whoever touches a system next deepens its entry to chest-standard before
closing the session. `node scripts/kbCoverage.mjs` §5 reports depth
(warn-only, never fails CI).

## Ownership (parallel sessions)

Entries may carry optional `owner:` + `experiment:` frontmatter naming the
session/area with in-flight uncommitted work (e.g. `owner: lighting`). Check
these fields before touching another session's active area, and set them when
starting an experiment that changes live visuals. The reverse index
`kb/code-index.json` (regenerated by every coverage run; consumed by
`kbRead --file`) answers "which entries constrain this file" — use it to find
the owner.

## Runtime linkage & change gate

- `kb/kb-links.json` (regenerated by every coverage run) maps registry id →
  KB entry: exact slug match first, fuzzy fallback. `/blocks.html` uses it
  for exact per-card pills (`kbEntry(name, id)`); a future in-game debug
  overlay can consume the same file.
- `node scripts/kbTouch.mjs` (warn-only; `--strict` to fail) maps the working
  tree against the reverse index at session close-out: every touched source
  file lists its owning entries and flags untouched owners.

## Layout

```
kb/
  README.md               ← this file
  index.json              ← machine index: id → { path, title, tags, status, updated }
                           (regenerate with `node scripts/syncKbIndex.mjs`; CI gate `npm run kb:check`)
  _templates/entry.md     ← front-matter template for new entries
  blocks/                 ← one file per block (or block family)
  entities/               ← mobs, animals, villagers, squid, boat, paintings
  mechanics/              ← cross-cutting systems (inventory, crafting, furnace, lighting, fluids, worldgen, multiplayer)
  ui/                     ← HUD/inventory/crafting/furnace/villager-trade/portal/world-map/options semantics
  terrain/                ← biomes & dimensions (beach, nether, biomes)
```

## Entry front matter (all entries must have this)

```yaml
---
id: blocks/chest
title: Chest
kind: block            # block | entity | mechanic | ui | system
wiki: https://minecraft.wiki/w/Chest
game_version: "1.19.3 (Java)"   # version our assets target
fetched_at: 2026-08-27
updated_at: 2026-08-27
status: implemented   # implemented | partial | absent | broken
tags: [storage, container, axe]
related_docs: [docs/CHEST_MODEL_SPEC.md]
---
```

Required sections inside the body: `## Vanilla specs`, `## Our implementation`,
`## Deviations / limitations`, `## Ruleset when modifying`, `## Open work`.

## Index maintenance

`index.json` is the fast path — keep it in sync whenever an entry is added or its
status changes. Format:

```json
{
  "blocks/chest": {
    "path": "blocks/chest.md",
    "title": "Chest",
    "tags": ["storage", "container"],
    "status": "implemented",
    "updated": "2026-08-27"
  }
}
```

## Tooling (keeping the KB live)

These scripts prevent the two failure modes: drift (an entry's `status`/anchors
lie) and gaps (objects that exist but no entry).

- `node scripts/syncKbIndex.mjs` — regenerate `index.json` from entry
  front-matter. `--check` validates id↔path consistency (no orphans).
- `node scripts/kbCoverage.mjs` — **anchor liveness + coverage reconciliation**.
  For every entry it verifies cited code anchors (`file:line`) still exist (fails
  CI on a dead anchor), and reconciles `catalog/completeRegistry.json` against
  documented subjects, grouped by registry `category`. Writes
  `kb-coverage-report.md`. Illustrative/planned anchors (no file yet) are reported
  but do not fail.
- `node scripts/kbWiki.mjs` — **wiki cross-check**. Fetches minecraft.wiki
  category members (live MediaWiki API) and reports wiki objects with no registry
  entry (don't exist in the game) and objects in the game but undocumented in the
  KB. Use `--from <file.json>` for an offline title list, `--cat <Category>` to
  scope. Network-dependent; not wired into CI.
- `node scripts/kbRead.mjs <topic>` / `--file <src/path>` — **always-read
  lookup**. Run BEFORE touching a block/entity/mechanic; it ranks matching
  entries and prints the `kb/...` files to read. Exits 1 on no match (meaning:
  create the entry first). `npm run kb:read -- torch`.
- `node scripts/kbExpand.mjs` — **auto-expand**. Dry-run by default: reports
  registry objects + implemented biomes (`kb == null`) with no KB entry,
  grouped by category. `--write --limit N` creates stubs from
  `_templates/entry.md` (never overwrites) and re-syncs `index.json`;
  `--category <cat>` / `--include blocks|biomes` scope it. This is how the KB
  keeps growing toward full game-design coverage (see `kb-coverage-report.md`).
- `node scripts/kbConform.mjs` — **conformance suite: the game obeys the KB**.
  Asserts KB-declared specs against game data (trade label↔id consistency,
  slot shapes, biome linkage, `usesLeft` derivation, fluid/recipe id
  resolution), each failure citing the violated entry. Runs as the third leg
  of `npm run kb:check`; exit 1 on drift.

## Executable specs (entries declare enforcement)

An entry opts into enforcement with a single-line JSON `spec:` frontmatter
key, e.g. `spec: {"tradeIds": true}` or
`spec: {"slots": {"invMain": 27, "hotbar": 9, "chest": 27}}`. `kbConform.mjs`
runs only declared assertions (unknown keys fail as typos) and reports which
entries declare what. Numbers in deep entries should migrate here: prose
stays human, numbers become load-bearing.

Run `npm run kb:check` (sync + coverage) as part of the machine gates; add
`npm run kb:wiki` ad-hoc when auditing coverage against the wiki.
